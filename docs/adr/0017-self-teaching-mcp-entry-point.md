# Self-teaching MCP entry point and on-demand Aksel snippet resources

The Desktop Arcade MCP server teaches a zero-knowledge agent through a tiny always-on entry point and pulls Aksel component knowledge only on demand, so guidance never narrows what the agent thinks Arcade can build and component data never enters context until a component is actually used. On connect, `initialize.result.instructions` carries only the **Arcade authoring** mechanics the agent cannot infer elsewhere — the import-free sandbox, `goToPage`/`Link` navigation against app-assigned page ids, `{{pageRef:name}}` batch ordering, and the apply→diagnostics→capture loop — plus a pointer to `arcade://desktop/authoring-guide`. It deliberately carries no component list and no worked example, because an example like a "3-page form" anchors scope; mechanic snippets in the authoring guide are labelled as illustrating wiring, not a use case.

Per-component usage is **pull, not push**: the authoring guide names three reach paths in priority order — the version-matched `arcade://aksel/catalog` index plus one `arcade://aksel/components/{name}` snippet resource at a time, then `https://aksel.nav.no/llm.md`, then the separate Aksel MCP tools if the client has them. The Aksel snippet resources are generated from the curated **Aksel insertion catalog** (`src/data/akselCatalog.ts`, pinned to `AKSEL_CATALOG_VERSION`) into a committed shared contract artifact at `src/shared/desktopMcp/akselCatalogData.generated.ts` via `npm run aksel:refresh-mcp-catalog`, with a legacy CommonJS mirror kept for handwritten-server parity checks. This keeps the SDK-backed Desktop MCP runtime on typed shared data while drift tests still guard the generated artifacts against the builder. A separate `arcade://desktop/apply-changes-operations` reference documents the per-operation field matrix because `apply_changes` operations share one schema.
