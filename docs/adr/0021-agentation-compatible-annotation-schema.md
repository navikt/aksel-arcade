# Use an Agentation-compatible annotation schema

Arcade annotations use the Agentation annotation record as their durable compatibility envelope, with an Arcade-required page id added so every annotation belongs to exactly one Arcade page. Element targets remain connected to the rendered preview by identity first and live marker geometry second; Agentation coordinate and bounding-box fields are kept for compatibility and diagnostics, not as substitute anchors for responsive layouts. Visible marker positions are recomputed from live resolved targets on preview render, resize, and scroll instead of relying on stored coordinates. Arcade must not modify user-authored Arcade project source to add annotation IDs or data attributes. Unlike Agentation's empty-area drag fallback, Arcade v0.3.0 annotations must attach to one or more resolved preview elements; a drag that selects no meaningful elements does not create a coordinate-only annotation and does not show an error. When the user selects text, Arcade captures the selected text as annotation metadata but still anchors the annotation to the containing normalized element target rather than to a text-range-specific anchor. When a target cannot be resolved unambiguously, including when it has zero matches or multiple plausible matches, Arcade treats the annotation target as dead for the current preview: the annotation remains in project data for history and share/export, but it is not counted, shown as a normal marker, or returned through normal Desktop MCP annotation tools/resources, and Arcade must not place it from saved geometry or guess a target. A resolved target that is hidden by the current viewport or layout remains open/countable and visible to MCP without a separate visibility metadata contract; agents can inspect source and Preview evidence when viewport-specific visibility matters. Multi-element targets are all-or-nothing for resolution: if any selected element cannot be resolved unambiguously, the annotation is dead for the current render; if all resolve, Annotation mode may render the visible subset by outlining every visible selected element and placing one marker on the union bounding box of those visible resolved elements. The v0.3.0 PRD must require a target-resolution test matrix for common Aksel components and layouts before the feature is accepted. Dead-target state is derived from the current render, so an annotation becomes usable again if its target later resolves. Human single-annotation delete and the page-scoped Clear annotations action hard-delete annotation records rather than marking them dismissed; Clear annotations removes every annotation record for that page, including visible annotations, hidden status history, and currently dead-target records. Human-created annotations leave `authorId` unset because Arcade has no account model; thread-compatible human records use a generic `human` role if needed. A human edit to an acknowledged annotation resets its status to `pending` so agents see the changed feedback as new work. Human edits preserve any existing thread unchanged and update only the top-level comment, status, and timestamps in v0.3.0 because the human UI does not expose thread authoring. Arcade excludes Agentation's `_syncedTo` local sync bookkeeping from durable project data, while preserving optional Agentation protocol fields such as status, thread, intent, severity, and known future placement or rearrange data. The v0.3.0 Arcade UI creates and normal MCP tools act on ordinary feedback annotations only; known non-feedback kinds are preserved but hidden/ignored until a later UI/workflow supports them, and unknown kinds are rejected on import/share.
