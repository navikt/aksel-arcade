# Pages-aware agent bridge

The **Agent bridge** is extended so an **External agent** always reads and changes an **Arcade project** through the full pages-based **Arcade project source** model, but the page set is mutated through explicit lifecycle operations (create, rename, delete, set start page, select active page) rather than by submitting a whole replacement document. The agent read-state exposes **Global config**, the ordered **Arcade pages** with their stable ids and display names, the **start page**, and the **active page**. Even a one-page project is represented as a one-page pages-based source model, and an **Agent change** that edits code targets a specific page id or the Global config. Crucially, the app assigns the frozen `pageNN` ids on creation and returns them to the agent; the agent never chooses an id, it only references ids the app has already minted.

We rejected the declarative whole-document alternative (agent submits the entire `{globalConfig, pages[], startPageId}` and the app diffs it) because deletion-by-omission is dangerous with a generative agent: a single forgotten page would silently destroy work, and round-tripping ids through the agent invites violations of the frozen-id invariant (ADR 0012). Explicit operations keep id assignment authoritative in the app, make each structural change individually reviewable under the existing apply-then-review model, and let page CRUD stay under the existing `sourceChanges` permission without inventing a new capability. Earlier rollout work temporarily mirrored the experimental human multi-page flag, but once Arcade project source became permanently pages-based the Agent bridge had to match the same always-pages-aware contract as the rest of Desktop Arcade. The costs are a larger command surface to document and maintain; the benefit is that agent editing stays safe, auditable, and consistent with how humans author the same project.
